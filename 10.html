The internal representation of real numbers by a computer inevitably leads to some errors, even if the numerical method we use is exact. Indeed, the basic observation that there are infinitely many real numbers, but the memory of any computer is finite, leads immediately to the conclusion that some kind of rounding must be happening at the step of storing the numbers in the memory.

I already discussed the binary representation of numbers in Section 8.3. Hopefully not surprisingly, it is the one that is used to represent numbers internally (so that an elementary unit of memory, which is 1 bit, corresponds to either 0 or 1). The numbers of type float in Python (and in NumPy) are stored using 64 bits. By simple arithmetic I see that for 64 bits the total amount of different numbers is just \[ 2^{64} = 18{,}446{,}744{,}073{,}709{,}551{,}616, \] which is not that much since I need my numbers to represent objects at any scale. So, an immediate and naive idea to space \(2^{64}\) different numbers at equal steps should be put aside. Instead the floating-point numbers (type float) are represented using the IEEE 754 standard, where one bit is used to represent the sign \(s\in\{0,1\}\) of the number (\(s=0\) for plus and \(s=1\) for minus), 11 bits are devoted to the exponent \(e\) (such that we have \(2^{11}=2048\) values of our exponents) and finally the remaining 52 bits \(b_1,\ldots,b_{52}\) are used to store the fractional part \[ f=(0.b_1b_2\ldots b_{52})_2=\sum_{k=1}^{52}b_k2^{-k},\quad 0\leq f<1, \] of the number. So, in a nutshell the exponent describes how small and how big numbers we can represent, and the fractional part is responsible for the accuracy of representation. To put things together, any normal floating-point number \(x\) (that is, with \(1\leq e\leq 2046\)) is written as \[ x=(-1)^s \cdot 2^{e-1023}\cdot (1+f). \] Note that we have a bias \(-1023\) in the exponent to be able to represent negative exponents, and the leading bit of any normal number we represent is 1 (because of \((1+f)\) in the formula). The given representation does not allow one to store 0, for instance, and even if it did, there would always be a (relatively) large gap between zero and the closest nonzero number. For this reason in the IEEE 754 standard the special case \(e=0\) (i.e., all 11 bits are zero) is treated differently. In this case we get so-called subnormal numbers of the form \[ x=(-1)^s\cdot 2^{-1022}\cdot(0+f), \] which allow one to store \(x=0\) (\(f=0\)), and fill the gap between 0 and the closest nonzero normal numbers.

The second special case is \(e=2047\) (i.e., all the bits are ones). If \(f\neq 0\) then in this case the result is NaN (“Not a Number”); if \(f=0\) the result is \(+\infty\) for \(s=0\) and \(-\infty\) for \(s=1\).

10.1Toy number system

Instead of dealing with 64 bit numbers, let me consider a toy number system, to get a feeling for how such floating-point numbers behave, and when one can expect something not very pleasant from a computational point of view. So I will take \(e\) to be \(3\) bits, so that I can represent 8 different exponents \(e\in\{0,1,\ldots,7\}\), my bias is \(4\), so that my actual exponents are \(E=e-4\in\{-4,-3,-2,-1,0,1,2,3\}\), and \(f\) to be two bits, so that any nonzero number in my toy system is \[ x=(-1)^s\cdot (1.b_1b_2)_2\cdot 2^{E},\quad E\in\{-4,-3,\ldots,3\}. \] Unlike IEEE 754, I do not reserve any exponent patterns for special values: all 8 exponents are used for normal numbers. I also include the number \(0\) in my system. The smallest positive number I can represent hence is \(2^{-4}=1/16\), and the largest one is 14 (\(2^3\cdot 1.75=14\)). The total number of positive numbers is 32. The closer to zero, the closer my numbers are to each other, and further from zero the numbers start separating more, which also happens in the 64 bit IEEE 754 standard.

More details can be seen in Fig. 10.1.

Note that there are no numbers between 0 and \(1/16\); this is exactly the reason the actual system needs subnormal numbers. I will ignore them for simplicity in my examples. Also, in my system \(\epsilon=0.25\) is the machine epsilon, which is the distance from 1 to the next larger number in the system (recall Exercise 2.7, where you found the machine epsilon of the float numbers; note also that from now on \(\epsilon\) denotes the machine epsilon, and not a tolerance as in Section 3). As shown below, the machine epsilon controls the relative error of floating-point arithmetic implemented in the system.

To do arithmetic in my system I note that rounding happens in two steps: first, given two real numbers \(x,y\in\R\), I need to represent them as numbers of my system, then I do arithmetic on them, and the result of the arithmetic operation again should be rounded. Let me formally define my rounding procedure: for any real \(x\in \R\), \(R(x)\) means the closest representable number in my system (see Fig. 10.1), and if there are two closest numbers, the one that is an even multiple of the spacing is chosen. Since \(0\) belongs to my system, all \(x\) with \(|x|\leq 1/32\) are rounded to \(R(x)=0\) (underflow). If \(|x|\geq 15\), then \(x\) cannot be rounded to any number of my system, and I say that overflow occurs. So, what is actually happening if I need to compute \(x+y\) is the following: \[ x\oplus y=R\bigl(R(x)+R(y)\bigr), \] where \(x\oplus y\) belongs to my number system, and in general \(x\oplus y\neq x+y\). The other arithmetic operations are computed in the same way.

Finally, let me explain why the machine epsilon gives the size of the error. All numbers of my system in the interval \([2^E,2^{E+1})\) have the same exponent \(E\), and hence the spacing between two neighboring numbers there is \(\epsilon\cdot 2^E\). Rounding to the closest number changes \(x\in[2^E,2^{E+1})\) by at most half of this spacing, and since \(|x|\geq 2^E\), \[ \frac{|R(x)-x|}{|x|}\leq \frac{\epsilon\cdot 2^E}{2\cdot 2^E}=\frac{\epsilon}{2}\,,\quad \frac{1}{16}\leq |x|\leq 14. \] The number \(\epsilon/2\) is called the unit roundoff. In my toy system \(\epsilon/2=0.125\), and in the 64 bit IEEE 754 standard \(\epsilon=2^{-52}\approx 2.2\cdot 10^{-16}\).

Now I consider a few examples that highlight how using the floating-point number system leads to computational errors.

Example 10.1 (Representation error: \(0.1+0.2\neq 0.3\)). Let me compute \(0.1+0.2\) in my system. None of the three numbers \(0.1\), \(0.2\), \(0.3\) belongs to my system (in binary, \(0.1=(0.000110011\ldots)_2\) has an infinite expansion), so first they must be rounded. The number \(0.1\) lies between \(1/16\) and \(1/8\), where the spacing is \(1/64\) (see Fig. 10.1). Since \(0.1=6.4/64\), the closest number is \(6/64\), that is, \[ R(0.1)=\frac{3}{32}\,. \] In the same way, \(0.2=6.4/32\) lies between \(1/8\) and \(1/4\), where the spacing is \(1/32\), and \(0.3=4.8/16\) lies between \(1/4\) and \(1/2\), where the spacing is \(1/16\). Hence \[ R(0.2)=\frac{6}{32}=\frac{3}{16}\,,\quad R(0.3)=\frac{5}{16}\,. \] Now I add the stored numbers: \[ R(0.1)+R(0.2)=\frac{3}{32}+\frac{6}{32}=\frac{9}{32}=\frac{4.5}{16}\,, \] which lies exactly halfway between \(4/16\) and \(5/16\). The tie goes to the even multiple of the spacing, and therefore \[ 0.1\oplus 0.2=R\left(\frac{9}{32}\right)=\frac{1}{4}\neq\frac{5}{16}=R(0.3). \] So, if I ask my system whether \(0.1+0.2\) equals \(0.3\), the answer is “no.”

The same rounding errors can also accumulate. Consider a clock that adds \(0.1\) second at every tick, that is, \(t_0=0\) and \(t_k=t_{k-1}\oplus 0.1=R\bigl(t_{k-1}+R(0.1)\bigr)\). Then \begin{align*} t_1&=R\left(\frac{3}{32}\right)=\frac{3}{32}\,, & t_2&=R\left(\frac{3}{32}+\frac{3}{32}\right)=\frac{3}{16}\,,\\ t_3&=R\left(\frac{3}{16}+\frac{3}{32}\right)=R\left(\frac{9}{32}\right)=\frac{1}{4}\,, & t_4&=R\left(\frac{1}{4}+\frac{3}{32}\right)=R\left(\frac{11}{32}\right)=\frac{3}{8}\,,\\ t_5&=R\left(\frac{3}{8}+\frac{3}{32}\right)=R\left(\frac{15}{32}\right)=\frac{1}{2}\,, & t_6&=R\left(\frac{1}{2}+\frac{3}{32}\right)=R\left(\frac{19}{32}\right)=\frac{5}{8}\,,\\ t_7&=R\left(\frac{5}{8}+\frac{3}{32}\right)=R\left(\frac{23}{32}\right)=\frac{3}{4}\,, & t_8&=R\left(\frac{3}{4}+\frac{3}{32}\right)=R\left(\frac{27}{32}\right)=\frac{7}{8}\,,\\ t_9&=R\left(\frac{7}{8}+\frac{3}{32}\right)=R\left(\frac{31}{32}\right)=1, & t_{10}&=R\left(1+\frac{3}{32}\right)=R\left(\frac{35}{32}\right)=1, \end{align*} where \(t_3\), \(t_4\), and \(t_5\) are ties. My clock shows one second already after 9 ticks instead of 10. Even worse, it stops: near 1 the spacing is \(1/4\), and \(3/32\) is less than half of it, so \(1\oplus 0.1=1\), and the clock shows one second forever. The 1991 Patriot missile failure had the same root cause: \(0.1\) is not representable in binary. The system computed the time by multiplying the number of ticks by a 24-bit approximation of \(0.1\), and after about 100 hours of operation the computed time was off by about \(0.34\) seconds.

Note that the previous example also shows the so-called absorption, when adding a nonzero number does not change the result. Convince yourself that \(8\oplus 1=8\) in my toy system (compare with \(10^{16}+1=10^{16}\) in Section 1).

Example 10.2 (Catastrophic cancellation). Another, much more dangerous, source of errors is the subtraction of two close numbers. Let me compute \(1.3-1.2\) in my system. Both numbers lie between \(1\) and \(2\), where the spacing is \(1/4\) (see Fig. 10.1). Since \(1.3=5.2/4\) and \(1.2=4.8/4\), both of them are rounded to the same number: \[ R(1.3)=\frac{5}{4}\,,\quad R(1.2)=\frac{5}{4}\,. \] The relative errors of these roundings are only about \(4\%\), well below \(\epsilon/2=1/8\). However, \[ 1.3\ominus 1.2=R\left(\frac{5}{4}-\frac{5}{4}\right)=0, \] whereas the exact answer is \(1/10\), i.e., the relative error is \(100\%\). Note that the subtraction itself is exact; the whole error comes from the rounding of the inputs. Similarly, \(R(1.4)=6/4=3/2\) and \(R(1.1)=1\), and hence \[ 1.4\ominus 1.1=R\left(\frac{3}{2}-1\right)=\frac{1}{2} \] instead of \(3/10\), which is a \(67\%\) error.

To see why this happens, let \(R(x)=x(1+\delta_1)\) and \(R(y)=y(1+\delta_2)\) with \(|\delta_1|,|\delta_2|\leq\epsilon/2\). Then \[ \frac{\bigl(R(x)-R(y)\bigr)-(x-y)}{x-y}=\frac{x\delta_1-y\delta_2}{x-y}\,, \] and if \(x\) and \(y\) are close, the small numerator is divided by the small number \(x-y\). The leading digits of \(x\) and \(y\) cancel, and what remains is mostly the rounding error.

Example 10.3 (Gaussian elimination without pivoting). Consider the system \[ \begin{aligned} \frac{1}{16}\,x_1+x_2&=1,\\ \frac{1}{2}\,x_1+\frac{1}{2}\,x_2&=1, \end{aligned} \] whose exact solution is \(x_1=16/15\), \(x_2=14/15\). The best my system can do is \(R(16/15)=1\), \(R(14/15)=7/8\).

Without pivoting, I use \(1/16\) as the pivot. The multiplier is \(m=8\), and eliminating \(x_1\) from the second equation gives \[ R\left(\frac{1}{2}-8\cdot 1\right)=R\left(-\frac{15}{2}\right)=-8,\quad R(1-8\cdot 1)=-7, \] where \(-15/2\) is a tie between \(-7\) and \(-8\). Back substitution yields \[ x_2=R\left(\frac{-7}{-8}\right)=\frac{7}{8}\,,\quad x_1=R\left(\frac{1-7/8}{1/16}\right)=2. \] The value of \(x_2\) is fine, but \(x_1=2\) is almost twice the exact \(16/15\). The reason is in the last step. The subtraction \(1-x_2=1/8\) is exact, but \(x_2=7/8\) already has an error (the exact value is \(14/15\)), and since \(1-x_2\) is small, this error becomes a large relative error of \(1-x_2\) (cancellation again); then it is divided by the small pivot \(1/16\), i.e., multiplied by \(16\).

With partial pivoting, I first swap the equations, so that the pivot is \(1/2\) and the multiplier is \(m=1/8\). Now \[ R\left(1-\frac{1}{8}\cdot\frac{1}{2}\right)=R\left(\frac{15}{16}\right)=1,\quad R\left(1-\frac{1}{8}\cdot 1\right)=\frac{7}{8}\,, \] and back substitution gives \[ x_2=\frac{7}{8}\,,\quad x_1=R\left(\frac{R(1-7/16)}{1/2}\right)=R\left(\frac{1/2}{1/2}\right)=1, \] which is the best possible answer in my system. The matrix and the arithmetic are the same; only the order of the equations has changed. With pivoting, the multipliers satisfy \(|m|\leq 1\), which limits the growth of the rounding errors. This is the explanation, promised in Section 9.6, of why np.linalg.solve, which uses partial pivoting, was hundreds of times more accurate than my functions without pivoting.

10.2Floating-point numbers in Python

All the effects from my toy system can be observed with the actual float numbers, they just happen in the 16th digit instead of the first one:

>>> 0.1 + 0.2 == 0.3
False
>>> 0.1 + 0.2
0.30000000000000004
>>> 1.0 + 2.0**-52 == 1.0     # 2^(-52) is the machine epsilon
False
>>> 1.0 + 2.0**-53 == 1.0     # half of it is absorbed
True
>>> 1e16 + 1.0 == 1e16        # absorption, recall Section 1
True
>>> 1.3 - 1.2                 # cancellation
0.10000000000000009
>>> 1e308 * 10                # overflow: the result is infinity
inf
>>> 1e-320                    # a subnormal number
1e-320
>>> 1e-330                    # underflow: the result is zero
0.0

The last two lines are underflow: numbers below \(2^{-1022}\approx 2.2\cdot 10^{-308}\) are subnormal, and below about \(5\cdot 10^{-324}\) they are rounded to zero. Here is the clock from Example 10.1:

t = 0.0
for k in range(10):
    t += 0.1
print(t, t == 1.0)
0.9999999999999999 False

In fact, we have already met floating-point effects many times in these notes:

  • In Section 1 the arithmetic algorithm for switching the values of two variables failed for a = 1e16, b = 1.0: this is absorption.

  • In Exercise 2.7 you found the machine epsilon \(\epsilon=2^{-52}\).

  • In Exercise 2.13 the quadratic formula gave an inaccurate smaller root for \(b=10^8\): this is catastrophic cancellation.

  • In Section 3 the bisection interval stopped shrinking at two neighboring float numbers, and a tolerance smaller than the gap between them could not be reached; similarly for the function newton in Section 6.2, which also returned \(\sqrt 2\) with an error in the last digit.

  • In Exercise 6.2 the Newton–Raphson method stalled at about 8 correct digits, because of cancellation in \(e^x-x-1\) for small \(x\).

  • In Section 9.5 np.linalg.det returned \(-20.000000000000007\) instead of \(-20\), and in Section 9.6 pivoting made the solution much more accurate (Example 10.3).

10.3Numerical differentiation

Consider now a practically important example of computing the derivative of a given function \(f\) at a given point \(x\) numerically.

A very straightforward approach is to use the definition \[ f'(x)=\lim_{h\to 0}\frac{f(x+h)-f(x)}{h}\,, \] to approximate \[ f'(x)\approx \frac{f(x+h)-f(x)}{h}\,, \] for a fixed \(h\). Naively, one may think that the smaller \(h\) is chosen, the better will be the approximation. Indeed, by Taylor’s formula I have \[ f(x+h)=f(x)+f'(x)h+\frac{f''(\xi)}{2}h^2, \] so mathematically, the order of the error I am making is \(\mathcal O(h)\) since from the last formula \[ \frac{f(x+h)-f(x)}{h}-f'(x)=h\,\frac{f''(\xi)}{2}\,, \] which tends to 0 if \(h\to 0\).

However, recall from Example 10.2 that when I subtract two close numbers (which \(f(x+h)\) and \(f(x)\) will be for small \(h\)), catastrophic cancellation happens, and the difference contains noise of the order \(\epsilon |f(x)|\). Hence the total error \(E(h)\) in my calculation comes from two sources: the error of the method, and the rounding error: \[ E(h)\leq \frac{h}{2}\,|f''(\xi)|+\epsilon\,\frac{|f(x)|}{h}\,. \] To minimize this error, I replace \(f''(\xi)\) with \(f''(x)\) (which is reasonable for small \(h\)) and use the standard calculus technique by computing the derivative \(E'(h)\) and solving the equation \(E'(h)=0\) to find that the optimal step size for my numerical differentiation is \[ h=\sqrt{\frac{2|f(x)|}{|f''(x)|}}\,\sqrt{\epsilon}, \] that is, \(h\) in practice should be chosen of the same order as \(\sqrt{\epsilon}\). At this optimal \(h\) the error is \(E\approx\sqrt{2\epsilon\,|f(x)|\,|f''(x)|}=\mathcal O(\sqrt{\epsilon})\), so in the 64 bit arithmetic I can expect only about 8 correct digits out of 16.

To finish this section, consider a specific example of computing the derivative of \(f(x)=e^x\) at \(x=1\). The exact answer, of course, is \(f'(1)=e\). The following code computes the error of the approximation for many values of \(h\) at once and plots it, together with the bound \(E(h)\); here \(|f(x)|=|f''(x)|=e\), so that \(h_{\rm opt}=\sqrt{2\epsilon}\).

import numpy as np
import matplotlib.pyplot as plt

eps = np.finfo(float).eps       # machine epsilon, 2^(-52)


def f(x):
    return np.exp(x)


x = 1.0
exact = np.exp(1.0)             # f'(1) = e

h = np.logspace(-16, 0, 400)    # 400 values from 10^(-16) to 1
error = np.abs((f(x + h) - f(x)) / h - exact)

bound = h * np.exp(x) / 2 + eps * np.exp(x) / h     # E(h) with |f(x)| = |f''(x)| = e
h_opt = np.sqrt(2 * eps)
E_opt = np.sqrt(2 * eps) * np.exp(x)

k = np.argmin(error)            # the index of the smallest error
print(f"optimal h = {h_opt:.1e}, predicted error = {E_opt:.1e}")
print(f"best observed: h = {h[k]:.1e}, error = {error[k]:.1e}")

plt.loglog(h, error, ".", label="actual error")
plt.loglog(h, bound, "k-", label="the bound E(h)")
plt.axvline(h_opt, color="red")
plt.xlabel("h")
plt.ylabel("error")
plt.legend()
plt.show()
optimal h = 2.1e-08, predicted error = 5.7e-08
best observed: h = 1.1e-08, error = 3.3e-09

Note that the function f works with the whole array h at once, since np.exp acts elementwise; hence error and bound are arrays computed without any loops. Here np.finfo(float).eps is the machine epsilon of the float numbers, np.logspace(-16, 0, 400) gives 400 numbers from \(10^{-16}\) to \(1\) whose logarithms are equally spaced (similar to np.linspace), np.abs computes the absolute values elementwise, np.argmin returns the index of the smallest element of an array, plt.loglog plots in the logarithmic scale on both axes, and plt.axvline draws a vertical line. Fig. 10.2 shows the result (with some additional formatting).

Fig. 10.2 confirms the analysis. For large \(h\) the error decreases proportionally to \(h\), as the truncation error predicts. For \(h\) smaller than about \(10^{-8}\) the rounding error takes over, and the error grows as \(h\) decreases; for \(h\approx 10^{-16}\) even \(x+h=x\) in floating point, the computed derivative is \(0\), and the error is \(100\%\). Near the optimal step \(h_{\rm opt}=\sqrt{2\epsilon}\approx 2.1\cdot 10^{-8}\) the error is of order \(10^{-8}\), that is, only about half of the 16 digits are correct. The smallest observed error, \(3.3\cdot 10^{-9}\), is even below the predicted \(5.7\cdot 10^{-8}\); this is not a contradiction, since \(E(h)\) is an upper bound, and the actual rounding errors are often smaller than the worst case.

10.4Concluding exercise

In Example 10.3 the large error was caused by the algorithm, and pivoting fixed it. The following exercise shows that sometimes the problem itself is to blame, and then no algorithm can help.

Exercise 10.3. Consider the system \[ \begin{aligned} x_1+x_2&=2,\\ x_1+1.2\,x_2&=2.2. \end{aligned} \]

  1. Check that the exact solution is \(x_1=1\), \(x_2=1\).

  2. Show that in my toy number system \(R(1.2)=5/4\) and \(R(2.2)=2\), so that the system that my computer actually stores is \[ \begin{aligned} x_1+x_2&=2,\\ x_1+\frac{5}{4}\,x_2&=2. \end{aligned} \] Solve this system by Gaussian elimination in my system and show that all the arithmetic is exact, and yet \(x_1=2\), \(x_2=0\). Explain geometrically, by drawing the two lines given by the equations, why a tiny change of the data moves the solution so far.

  3. Write the original system as \(\bs A\bs x=\bs b\). Plug \(\bs x=(2,\,0)^\top\) into it and show that the residual \(\bs b-\bs A\bs x\) is \((0,\,1/5)^\top\), which is of the size of the rounding errors of the data in my system (\(\epsilon/2=12.5\%\) of \(2.2\) is about \(0.27\)). Conclude that a small residual does not guarantee that the solution is accurate.

  4. Would partial pivoting, or any other algorithm, give a better answer? Explain the difference between this exercise and Example 10.3.
