In the last section I showed that the code that implements Cramer’s method runs very slowly even for small \(n\), namely, for \(n=9\). Gaussian elimination, contrary to this, was able to solve a system of \(300\) equations with \(300\) unknowns in quite a manageable time. The goal of this section is to give a precise mathematical formalization of this phenomenon.

8.1Counting the operations

Since the time required for a certain algorithm to run depends on the details of the hardware we use, it is more representative to count the number of some elementary operations, such as multiplications, divisions, additions, and subtractions. Strictly speaking, these operations do not take the same time (on modern processors additions and multiplications take about the same time, but divisions are noticeably slower), and sometimes they should be counted separately; here, however, I will count everything together.

I start with Cramer’s method and recall that to solve a system of \(n\) equations with \(n\) unknowns I need to calculate \(n+1\) determinants. Let \(D_n\) be the number of elementary operations that are necessary to calculate the determinant of an \(n\times n\) matrix. Clearly I have that \(D_2=2+1=3\), i.e., I need to perform two multiplications and one subtraction. Now, to compute \(D_3\), I recall that I need to compute 3 determinants of \(2\times 2\) matrices, multiply them by the elements of the first row, and make two additions/subtractions, in other words, \[ D_3=3D_2+3+2. \] Generalizing to an arbitrary \(n\), I get \[ D_n=nD_{n-1}+n+(n-1)=nD_{n-1}+2n-1, \quad D_2=3, \] which is a linear difference equation, which in principle can be solved exactly. Since at this point I do not care too much about the exact result (but see Exercise 8.1), I consider instead a smaller number \(d_n\), for which \[ d_n = n d_{n-1},\quad d_2=3, \] such that clearly \(d_n<D_n\) for any \(n>2\) (that is, I am computing a very conservative lower estimate for \(D_n\)).

Since \[ d_n=nd_{n-1}=n(n-1)d_{n-2}=n(n-1)(n-2)\ldots4\cdot 3\cdot d_2>n(n-1)\ldots 4\cdot 3\cdot 2=n!, \] I can very conservatively estimate that \[ D_n> n!, \] and hence Cramer’s method requires a ridiculous number of elementary operations, at least \[ T_{\textup{Cramer}}=(n+1)n!=(n+1)! \] (a more careful analysis shows that this number is actually close to \(e(n+1)!\), see Exercise 8.1).

Now let me count the same operations for Gaussian elimination with back substitution. Recall that this method consists of two steps. First I transform \([\bs A\mid \bs b]\) into \([\bs U\mid \bs b']\), where \(\bs U\) is an upper triangular matrix. After this, I perform back substitution computing \(x_n,x_{n-1},\ldots, x_1\).

I start with the first step, which is done sequentially on \(n-1\) rows (I do not need to do anything when I get to the last row). Assume that at step \(i\) I have \[ \left[\begin{array}{cccccc|c} a_{11} & a_{12} &\ldots& \ldots & \ldots & a_{1n} & b_1\\ 0 & a_{22} & \ldots&\ldots & \ldots & a_{2n} & b_2\\ 0 & 0 & \ddots & & && \vdots\\ \vdots & && a_{ii} & \ldots & a_{in} & b_i \\ \vdots & & & a_{i+1,i} & \ldots & a_{i+1,n} & b_{i+1}\\ & && \vdots & &\vdots & \vdots\\ 0 && \ldots & a_{ni} & \ldots & a_{nn} & b_n\\ \end{array}\right]. \] How many operations do I need to perform to move to step \(i+1\)? Recall the formulas from Section 7. First, I compute the \(n-i\) multipliers \(m_{ji}=a_{ji}/a_{ii}\), \(j=i+1,\ldots,n\), which requires \(n-i\) divisions. Next, I modify the elements of the \((n-i)\times(n-i)\) submatrix of \(\bs A\) composed of the rows and columns with indexes \(i+1,\ldots,n\): each new element \(a'_{jk}=a_{jk}-m_{ji}a_{ik}\) requires one multiplication and one subtraction, hence \((n-i)^2\) multiplications and \((n-i)^2\) subtractions. Finally, for the \(n-i\) elements \(b'_j=b_j-m_{ji}b_i\) of vector \(\bs b\) I need \(n-i\) multiplications and \(n-i\) subtractions. Summarizing, multiplications/divisions are performed for the forward step of Gaussian elimination \[ M_f=\sum_{i=1}^{n-1}\left((n-i)^2+2(n-i)\right) \] times, and additions/subtractions are performed \[ A_f=\sum_{i=1}^{n-1}\left((n-i)^2+(n-i)\right) \] times. These sums can be calculated by recalling that \[ \sum_{k=1}^n k=\frac{n(n+1)}{2}\,,\quad\sum_{k=1}^n k^2=\frac{n(n+1)(2n+1)}{6}\,. \] I find that \[ M_f=\frac{2n^3+3n^2-5n}{6}\,,\quad A_f=\frac{n^3-n}{3}\,. \]

For the backward step first I need one division to find \(x_n\), then one multiplication, one subtraction, and one division to find \(x_{n-1}\), two multiplications, two subtractions, and one division to find \(x_{n-2}\), and so on, in total \[ M_b=n+\sum_{i=1}^{n-1}i=\frac{n(n+1)}{2} \] multiplications and divisions, and \[ A_b=\sum_{i=1}^{n-1}i=\frac{n(n-1)}{2} \] additions/subtractions.

Finally, the total numbers are \[ M_t=M_f+M_b=\frac{n(n^2+3n-1)}{3}\,,\quad A_t=A_f+A_b=\frac{n(2n^2+3n-5)}{6}\,, \] and the total number of operations is \[ T_{\textup{Gauss}}=M_t+A_t=\frac{2n^3}{3}+\frac{3n^2}{2}-\frac{7n}{6}\,. \] Clearly for sufficiently large \(n\) \[ T_{\textup{Gauss}}\approx\frac{2n^3}{3}\,. \]

As an example, let me take \(n=100\). A modern desktop computer can perform about \(10^{12}\) floating-point operations per second (one says that it performs at 1 teraflops; FLOP stands for a floating-point operation, and FLOPS for floating-point operations per second). For Gaussian elimination I get \[ T_{\textup{Gauss}}(100)=681550 \] operations, which gives me the time of about \(7\cdot10^{-7}\) seconds.

Now for Cramer’s method I find \[ T_{\textup{Cramer}}(100)= 101!\approx 9.426\cdot 10^{159} \] operations. Even the fastest supercomputers of today, which perform at more than \(10^{18}\) operations per second (exaflops), would need approximately \(3\cdot 10^{134}\) years for this computation (the best estimate we have nowadays for the age of our Universe is about \(13.8\cdot 10^9\) years). So, jokes aside, one should never (absolutely never, even for \(n=2\)) use Cramer’s method to solve a system of linear algebraic equations.

The formula for \(T_{\textup{Gauss}}\) can also be checked experimentally. If the time is proportional to the number of operations, then \(t(n)\approx Cn^3\) for large \(n\), hence \(\log t\approx \log C+3\log n\), and the points \((\log n,\log t)\) should lie close to a straight line with the slope 3. This is the same idea as for the order of convergence in Section 4.5. I continue with the code from Section 7 (the functions gauss_method and random_system):

import math
import time
import numpy as np

sizes = [50, 100, 200, 400]
times = []

for n in sizes:
    A, b, x_hat = random_system(n)
    t0 = time.perf_counter()
    gauss_method(A, b)
    t1 = time.perf_counter()
    times.append(t1 - t0)
    print(f"n = {n:3d}: {t1 - t0:.3f} seconds")

log_sizes = [math.log(n) for n in sizes]
log_times = [math.log(t) for t in times]
slope, shift = np.polyfit(log_sizes, log_times, 1)
print(f"slope = {slope:.2f}")
n =  50: 0.002 seconds
n = 100: 0.024 seconds
n = 200: 0.160 seconds
n = 400: 0.891 seconds
slope = 2.97

The slope is close to 3, as predicted. For small \(n\) the number of operations is not the only thing that matters (the program also spends time on calling functions, creating lists, etc.), which is one of the reasons why the slope is not exactly 3.

8.2Computational time complexity

What I estimated in the previous subsection is known as the computational time complexity of an algorithm. In general, computational complexity of an algorithm is the amount of resources required to run it. Two main resources are memory and time. I did not care much about memory (I invite you to think about how much memory each algorithm would require). The time complexity is usually counted in elementary operations (which could be multiplications, divisions, additions, subtractions, which we counted, and also assignments and function calls within the given code) versus the size of the input. In our case the input is specified by the number of unknowns \(n\).

The operations that I did not count can be important. For instance, in Section 7 solving a \(9\times 9\) system by Cramer’s method took about 3 seconds, and solving a \(300\times 300\) system by Gaussian elimination took about 0.3 seconds, although the numbers of arithmetic operations are comparable: about \(e\cdot 10!\approx 10^7\) and \(T_{\textup{Gauss}}(300)\approx 1.8\cdot 10^7\), respectively. The reason is that my recursive function det spends most of its time on something that I did not count: it calls itself millions of times and creates a new list (a submatrix) at each call.

In the majority of cases the exact number of operations is difficult (or even impossible) to calculate, and relatively small \(n\) are irrelevant; therefore, frequently, time complexity is computed asymptotically, in terms of the “big O” notation.

Definition 8.1. Let \(f,g\) be two real valued positive functions of integer argument \(n\). We say that \[ f(n)=\mathcal O\bigl(g(n)\bigr) \] (this reads “big O of \(g(n)\)”), if \[ f(n)\leq Mg(n) \] for all \(n\geq n_0\) and some constants \(M\) and \(n_0\).

So when someone says that the given algorithm has quadratic complexity, or big O of \(n^2\), it means that for sufficiently large \(n\) the number of operations that need to be performed for the algorithm to end is bounded above by the expression \(Mn^2\).

Using this definition I can say that Gaussian elimination has complexity \(\mathcal O(n^3)\) (since lower powers of \(n\) do not contribute for large \(n\)), or cubic complexity, whereas Cramer’s method has complexity \(\mathcal O((n+1)!)\), or factorial complexity.

A few words on terminology. An \(\mathcal O(1)\) algorithm is said to have constant time complexity, \(\mathcal O(\log n)\) — logarithmic complexity, \(\mathcal O(n)\) — linear complexity, \(\mathcal O(n^k)\) — polynomial complexity, \(\mathcal O(2^n)\) — exponential complexity.

Before I finish this subsection, I would like to make two important remarks. First, if there are two algorithms, one, say, \(\mathcal O(n^2)\) and the other one \(\mathcal O(n^3)\), it does not mean that the latter algorithm will perform slower in reality. Remember that the big O notation is asymptotic, and that for fixed finite \(n\) the constant \(M\) could be much larger for the quadratic algorithm than for the cubic one (\(1000\cdot10^2\) is of course bigger than \(10\cdot 10^3\)). Hence, while the asymptotic estimate of time complexity is important, for actual algorithms very often the exact number of elementary operations should be calculated or estimated, as it was done for Gaussian elimination and Cramer’s method.

Second, the asymptotic complexity, among other things, shows how much one can increase the size of the input \(n\) if the computational power grows (which has been happening since the creation of computers). Assume that we have \(R\) resources and we work on a problem that has exponential complexity \(\mathcal O(2^n)\), and the largest \(n\) we can afford to run is \(n=N\), so that \(R=2^N\). Assume also that our resources doubled: \(R'=2R\). How much can we increase \(N\)? Since \(R'=2R=2\cdot2^N=2^{N+1}\), for an algorithm with exponential complexity doubling the resources allows increasing the size of the input by 1! For a quadratic algorithm the same reasoning yields \(R'=2R=2N^2=(\sqrt{2}N)^2\), i.e., now we can increase our input by the factor \(\sqrt{2}\approx 1.41\), and for a cubic algorithm, such as Gaussian elimination, by the factor \(\sqrt[3]{2}\approx 1.26\). Convince yourself that for algorithms with logarithmic complexity I can square the size of the input, i.e., \(N'=N^2\). These simple informal arguments should convince you that developing algorithms with lower asymptotic time complexity is very important, even if they run slower for sufficiently small \(n\).

8.3One simple example: fast exponentiation and binary numbers

Before moving forward with numerical linear algebra, let me return to one example from Section 2, which shows how a better algorithm gives a very impressive improvement over a naive (but straightforward) approach. Recall that in Example 2.3 I computed \(a^n\) for a real number \(a\) and a natural number \(n\) in two ways: the function power_1 multiplies \(a\) by itself \(n\) times, and the function power_2 uses repeated squaring, and the latter was more than ten times faster for \(n=3147\). Now I can explain this precisely.

The function power_1 requires \(n\) multiplications, and therefore, according to the discussion above, the complexity of this algorithm is \(\mathcal O(n)\).

The idea of power_2 is the following. If \(n\) is a power of 2, say, \(n=16=2^4\), then the chain of squarings \[ a\to a^2=a\cdot a\to a^4=a^2\cdot a^2\to a^8=a^4\cdot a^4\to a^{16}=a^8\cdot a^8 \] requires not 15, but only 4 multiplications: knowing \(a^{2^j}\) I compute \(a^{2^{j+1}}=a^{2^j}\cdot a^{2^j}\) in one operation. What if \(n\) is not a power of 2? Then I use the binary representation of \(n\): \[ n=b_k2^{k}+b_{k-1}2^{k-1}+\ldots+b_12^1+b_02^0=\overline{b_kb_{k-1}\ldots b_1b_0}_2,\quad b_j\in\{0,1\},\quad b_k=1, \] which is exactly the same as the usual decimal representation, but with the base 2 instead of 10, and only two digits, 0 and 1, called bits. For instance, \(11=1\cdot2^3+0\cdot 2^2+1\cdot 2^1+1\cdot 2^0=\overline{1011}_2\). The digits can be computed by sequential division by 2 and recording the remainders: \(b_0\) is the remainder of the division of \(n\) by 2, \(b_1\) is the remainder of the division of \(\lfloor n/2\rfloor\) by 2, etc. Here is a function that does this.

def binary_digits(n: int) -> list:
    """Return the list [b_k, ..., b_1, b_0] of the binary digits of the natural number n."""
    digits = []
    while n > 0:
        digits.append(n % 2)    # the remainder is the next digit, starting with b_0
        n = n // 2
    return digits[::-1]         # reversed: the highest digit b_k first
>>> binary_digits(11)
[1, 0, 1, 1]
>>> binary_digits(3147)
[1, 1, 0, 0, 0, 1, 0, 0, 1, 0, 1, 1]
>>> bin(3147)
'0b110001001011'

The built-in function bin returns the binary representation of an integer as a string, with the prefix 0b.

Now, to compute \(a^n\) I actually compute \[ a^n=a^{\sum_{j=0}^k b_j 2^j}=\prod_{j=0}^{k}\left(a^{2^j}\right)^{b_j}, \] that is, I multiply together those of the numbers \(a,a^2,a^{2^2},\ldots,a^{2^k}\) for which \(b_j=1\). I need \(k\) multiplications to compute \(a^2,a^{2^2},\ldots,a^{2^k}\), and, in the worst possible case (when all the \(k+1\) digits of \(n\) are equal to 1), \(k\) more multiplications to compute the final product. Since \(2^k\leq n<2^{k+1}\), I have \(k=\lfloor\log_2 n\rfloor\), and the number of multiplications is at most \(2\lfloor\log_2 n\rfloor\). Hence this algorithm has logarithmic complexity \(\mathcal O(\log n)\), which is a huge improvement over the linear complexity of naive exponentiation. (The function power_2 from Section 2 does exactly this, see the hint there; it also performs one unnecessary multiplication by 1 at the beginning, so it needs at most \(2\lfloor\log_2 n\rfloor+1\) multiplications.)

In the spirit of this section, instead of measuring the time, let me count the multiplications directly, by adding a counter to the functions from Section 2:

import math


def power_1_count(a: float, n: int) -> tuple:
    """Return a**n computed as in power_1, and the number of multiplications."""
    count = 0
    c = 1
    for i in range(n):
        c *= a
        count += 1
    return c, count


def power_2_count(a: float, n: int) -> tuple:
    """Return a**n computed as in power_2, and the number of multiplications."""
    count = 0
    c = a
    d = 1
    while n != 0:
        if n % 2 == 0:
            n = n // 2
            c = c * c
        else:
            n = n - 1
            d = d * c
        count += 1          # exactly one multiplication at each step
    return d, count


n = 3147
result_1, count_1 = power_1_count(23, n)
result_2, count_2 = power_2_count(23, n)

print(result_1 == result_2)
print(f"power_1: {count_1} multiplications")
print(f"power_2: {count_2} multiplications")
print(f"the bound 2 floor(log2 n) + 1 = {2 * math.floor(math.log2(n)) + 1}")
True
power_1: 3147 multiplications
power_2: 17 multiplications
the bound 2 floor(log2 n) + 1 = 23

Here \(3147=\overline{110001001011}_2\), so \(k=11\), and power_2 performs \(k=11\) squarings and 6 multiplications, one for each digit 1. So the number of multiplications is reduced by the factor of about 185. Why then was power_2 “only” about 14 times faster in Section 2? Because the multiplications of large integers are not elementary operations of the same cost: in power_2 most multiplications involve numbers with thousands of digits (recall that \(23^{3147}\) has 4286 digits), whereas in power_1 one of the factors is always 23. This is one more illustration that one should always keep in mind what exactly is counted.

I think that this very simple example should convince you that spending time on improving an algorithm is not a waste of time.
